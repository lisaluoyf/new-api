## 1. 结论摘要

同一份 OpenCode 大上下文请求被定向回放到当时生产环境中全部 14 个已启用、且模型列表声明支持 `gpt-5.6-sol` 的渠道。每个渠道在最终矩阵中只保留一次结果。

结果如下：

- 只有渠道 `38 / openRouter` 完整成功。
- 渠道 `152 / change2pro-gpt-pro` 返回 HTTP 200，但 SSE 流内出现上下文超限错误；New API 却记录为成功并计费，属于严重的流式错误识别和账务一致性问题，不能算成功。
- 3 个渠道明确返回上下文窗口超限，但 HTTP 状态码分别被包装成 502 或 503。
- 1 个渠道明确返回协议不支持：模型虽然被配置为支持，但不支持 `/v1/chat/completions`。
- 2 个渠道只返回泛化的 `400 Bad Request`。
- 6 个渠道返回无具体模型错误正文的 Cloudflare 502/524。

最重要的判断：

1. 这份请求的真实输入规模约为 37.2 万至 37.3 万 Token，不是一百多万 Token。
2. `1,655,752` 是请求体字节数，不是 Token 数。
3. OpenCode 客户端显示 `373,358 tokens`，OpenRouter 成功响应返回 `372,168 prompt_tokens`，二者只相差约 0.32%，可以相互印证。
4. 请求并没有必然超过 `gpt-5.6-sol` 模型本身的上下文，因为渠道 38 已完整成功。
5. 不同渠道对同一模型的协议、最大上下文、最大输出、代理超时和大请求处理能力并不一致，不能只看模型名称判断能力。
6. 不能根据 400/502/503/504/524 状态码直接推断上下文超限；必须解析上游错误码和错误正文。
7. 之前尝试增加的“按大请求大小和几个 HTTP 状态码统一改写用户提示”的本地代码已经完整回滚，未发布。

说明：本文所称“唯一完整成功渠道”是生产配置中的 `openRouter` 渠道，并不等同于已经验证了 OpenAI 官方直连渠道。

## 7. 可能的总上下文校验差异

客户端不仅提交了约 37.2 万输入 Token，还请求：

```text
max_tokens=32,000
```

部分渠道可能按下面的方式校验上下文：

```text
prompt_tokens + max_tokens <= channel_context_limit
```

按 OpenRouter Usage 计算：

```text
372,168 + 32,000 = 404,168
```

按 OpenCode 显示计算：

```text
373,358 + 32,000 = 405,358
```

如果某些渠道的内部限制约为 400,000 Token，就会拒绝该请求。这个解释与数字高度吻合，但尚未通过降低 `max_tokens` 后重放验证。由于本次已明确要求每个渠道只发送一次，不能擅自重复回放验证。

## 11. 渠道 152 的严重异常

渠道：

```text
152 / change2pro-gpt-pro
```

回放内部 Request ID：

```text
202608160130574744466168268d9d6ORuemq3I
```

客户端实际收到的 SSE 流中包含：

```text
Your input exceeds the context window of this model.
Please adjust your input and try again.
```

但是 New API 日志记录为：

```text
type=2              # 成功消费日志
HTTP 200
prompt_tokens=286553
completion_tokens=1
use_time=16s
stream_status={"status":"ok","end_reason":"eof"}
accounting_status=ok
```

账务记录：

```text
accounting_channel_cost_amount_usd=0.0529478646
accounting_user_price_amount_usd=0.1058957293
accounting_user_final_amount_usd=0.1111905157
```

问题链路：

```text
上游返回 HTTP 200
→ SSE 流开始
→ SSE 中出现顶层 {"error": ...}
→ 当前 OpenAI Compatible 流处理器未识别顶层 error
→ 扫描器读到 EOF
→ EOF 被当作正常流结束
→ 本地估算 Usage
→ 写成功消费日志并计费
```

风险：

- 用户看到失败，但系统认为成功；
- 用户可能被扣费；
- 渠道成功率被错误抬高；
- Platform Billing 产生错误收入与成本；
- 不会生成 `final_failed` 快照；
- fallback 不会继续寻找可能成功的渠道；
- 同类请求难以通过现有错误日志发现。

这是本次诊断的 P0 修复项。

## 12. 本地 Token 估算偏差

渠道 152 没有返回可信 Usage，New API 使用本地 Token 估算：

```text
286,553 prompt tokens
```

而 OpenRouter 实际 Usage：

```text
372,168 prompt tokens
```

差值：

```text
85,615 tokens
```

本地估算低约 23%。

可能原因需要代码级验证：

- `gpt-5.6-sol` 使用了不匹配的 fallback tokenizer；
- Chat Completions 的工具消息、tool call 或工具结果没有全部计入；
- 工具定义或消息包装开销计算不完整；
- OpenCode 与 New API 对 assistant/tool 历史结构的序列化不同；
- OpenRouter 返回的 Usage 包含了本地估算未纳入的格式化 Token。

风险：

- 预扣不足；
- 大上下文路由阈值判断错误；
- 上游无 Usage 时结算偏低；
- 订阅滚动窗口用量偏低；
- Platform Billing 数据偏差。

这是本次诊断的 P1 修复项。

## 13. 为什么不能按 HTTP 状态码判断

本次相同的“上下文超限”语义分别出现为：

```text
502 + upstream_error
503 + context_too_large
200 + SSE error
```

同时，502 也可能是：

```text
Cloudflare Bad Gateway
源站连接失败
源站拒绝大请求
代理内部异常
长时间处理后断开
```

因此禁止实现类似下面的简单映射：

```text
502/503/504/524 + 大请求
→ 一律返回 context_too_large
```

正确分类顺序应为：

1. 解析结构化错误码；
2. 解析 JSON/SSE 顶层 error；
3. 识别明确的上下文错误语义；
4. 识别协议不支持、参数错误、限流、鉴权等明确语义；
5. 只有错误正文完全不透明时，才结合请求规模给出谨慎的通用建议；
6. 后台始终保留原始状态码、原始错误类别和原始渠道信息。

## 14. 当前路由能力缺口

当前渠道模型配置主要表达：

```text
该渠道是否声明支持某个模型名称
```

但本次验证说明还需要表达：

```text
supported_protocols
max_input_tokens
max_total_context_tokens
max_output_tokens
supports_large_tool_history
supports_stream
stream_error_format
```

已验证差异：

- 渠道 11 声明支持模型，但不支持 Chat Completions；
- 渠道 38 能完整处理约 37.2 万输入 Token；
- 渠道 25、52、160 明确拒绝；
- 渠道 152 以 HTTP 200 返回 SSE error；
- 其他渠道在代理层返回 400/502/524。

仅靠模型名称随机选路，会把可成功的请求先分配给无法处理的渠道。

## 15. 建议跟进任务

### P0：识别 OpenAI Compatible SSE 顶层错误

目标：任何 `data: {"error": ...}` 事件都不能被当作正常 Chat Completion chunk。

建议位置：

```text
relay/channel/openai/relay-openai.go
relay/helper/stream_scanner.go
```

验收条件：

- 能识别 SSE 顶层 `error`；
- 保存错误码、错误类型、错误消息和真实渠道；
- `StreamStatus` 标记为错误，不是 `ok/eof`；
- 不写普通成功消费日志；
- 生成失败日志和必要的失败快照；
- 未向用户输出内容时可以继续 fallback；
- 已向用户输出部分内容时，不重复 fallback，但必须记录 partial stream failure；
- 计费必须根据上游是否产生可信 Usage、是否输出内容、是否可能计费来决定；
- 增加单元测试覆盖“HTTP 200 + SSE error”。

### P0：审计“失败但成功记账”的历史请求

当前日志无法直接通过 `type=2` 判断客户端是否成功。建议增加：


### P1：大上下文感知路由

短期可以把渠道 38 标记为经过验证的长上下文渠道；长期必须通过配置和定期探测维护，不能永久硬编码某个渠道 ID。

需要同时考虑渠道成本，不能为了成功率无条件把所有大请求送到高成本渠道。

### P1：协议感知路由

渠道 11 不支持 `/v1/chat/completions`，不能仅因为模型列表包含 `gpt-5.6-sol` 就参与 Chat Completions 选路。

